1 Project Overview

The Distributed Job Scheduler is a decoupled, highly reliable asynchronous background processing platform designed to coordinate and execute distributed workloads across multi-worker fleets. It strictly enforces core distributed system invariants: at-least-once execution with atomic claiming, API-boundary idempotency, exponential backoff retry policies with jitter, and dead letter queue (DLQ) isolation.

Key Implemented Capabilities

  • Deterministic Job Lifecycle: Strict state machine transitions: QUEUED → CLAIMED → RUNNING → COMPLETED / FAILED → DEAD_LETTERED.
  • Atomic Compare-And-Swap (CAS) Claiming: Zero duplicate execution via atomic conditional updates at the SQL layer.
  • Idempotency Engine: Deduplication backed by unique indexes and Idempotency-Key request headers.
  • Exponential Backoff & Jitter: Dynamic future timestamp scheduling (runAt) without holding worker threads.
  • Dead Letter Queue (DLQ): Poison pill isolation, payload inspection, and manual/bulk replay.
  • Worker Fleet Mesh: Dynamic scaling, concurrency controls, and graceful SIGINT/SIGTERM shutdown.
  • Real-Time Observability: Push-based Server-Sent Events (SSE) streaming live metrics, state transitions, and execution Gantt timelines.

3 System Architecture

The system is architected as an asynchronous, decoupled processing pipeline:

+-----------------------------------------------------------------------------------+ | CLIENT LAYER: React Operations Dashboard | External REST Clients / SDKs | +----------------------------------------+------------------------------------------+ | HTTP Requests / Idempotency-Key v +-----------------------------------------------------------------------------------+ | API INGESTION: Express Gateway -> JWT Auth -> Idempotency Check -> Validation | +----------------------------------------+------------------------------------------+ | Persists Job (State=QUEUED) v +-----------------------------------------------------------------------------------+ | PRIMARY DATABASE (Prisma / SQLite / Postgres): ACID Store with Composite Indexes | +----------------------------------------+------------------------------------------+ | Polled by Scheduler & Workers v +-----------------------------------------------------------------------------------+ | SCHEDULER & WORKER FLEET ENGINE: | | * Scheduler Ticker: Promotes due delayed/cron jobs to QUEUED | | * Worker Fleet Mesh: Atomic CAS claim -> Concurrency Token -> Run -> Complete/DLQ | | * SSE Hub: Broadcasts real-time events to Dashboard | +-----------------------------------------------------------------------------------+

End-to-End Operational Lifecycle

  1. Ingestion: Client submits job via POST /api/jobs with an Idempotency-Key.
  2. Deduplication: Unique index verifies key; duplicate requests return cached results immediately.
  3. Scheduling: The scheduler ticker promotes due delayed/recurring jobs (runAt ≤ NOW) to QUEUED.
  4. Atomic Claim: Workers execute atomic CAS queries to acquire exclusive locks on eligible tasks.
  5. Execution: Worker runs the task payload within concurrency limits while updating heartbeats.
  6. Error & Retry: On failure, exponential backoff calculates future runAt. Exhausted retries route to DLQ.
  7. Telemetry: State transitions and logs stream live to connected dashboards via SSE.

Key Relational Decisions

  • UUID Primary Keys: Collision-resistant identifiers for distributed environments.
  • Composite Polling Indexes: CREATE INDEX idx_poll ON Job (queueId, state, priority DESC, runAt ASC);
  • Log Normalization: Heavy execution output stored in separate JobExecution records.

6 Reliability, Concurrency & State Machine

State Transition Logic

Initial State Trigger / Event Next State Guarantees & Action
SCHEDULED Scheduler Ticker (runAt ≤ NOW) QUEUED Promoted to active queue for worker polling.
QUEUED Worker Atomic CAS Claim CLAIMED Exclusive lock acquired; impossible for 2 workers to claim.
CLAIMED Execution Thread Starts RUNNING Execution recorded in JobExecution table.
RUNNING Task Completion (Success) COMPLETED Execution duration and logs saved; lock released.
RUNNING Task Error & Retries Remain QUEUED runAt updated with Exponential Backoff + Jitter.
RUNNING Task Error & Retries Exhausted DEAD_LETTERED Routed to DLQ with full error stack trace for triage.

Atomic Compare-And-Swap (CAS) SQL Claiming

UPDATE "Job"
SET "state" = 'CLAIMED',
    "lockedBy" = :workerId,
    "updatedAt" = CURRENT_TIMESTAMP
WHERE "id" = :targetJobId
  AND "state" = 'QUEUED';

7 Architectural Decisions & Trade-Offs

Decision Area Selected Approach Engineering Justification & Trade-Off
Storage Engine Relational DB (Prisma/SQLite) Provides full ACID guarantees, relational auditability, and durability across restarts. Trade-off: slightly higher polling overhead vs in-memory Redis, mitigated by composite indexes.
Live Telemetry Server-Sent Events (SSE) Lightweight, unidirectional HTTP/2 streaming with native browser reconnect. Avoids bidirectional WebSocket state overhead.
Task Allocation Worker Pull (Polling + CAS) Natural backpressure prevents worker memory exhaustion under traffic surges.
Retry Mechanism Future runAt Timestamps Zero thread blocking; worker slots remain 100% available for immediate tasks.
Idempotency API Gateway Boundary Stops duplicate jobs before database mutation or execution pipeline entry.
